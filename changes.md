1. Функциональное требование № 4
Краткое описание изменения: планировалось использовать готовый картографический/транспортный API (Яндекс.Карты) для расчёта транспорта между точками; стало — собственный сервер OSRM для пеших/автомобильных маршрутов и собственный GTFS-граф в OpenTripPlanner для общественного транспорта (метро, МЦК, МЦД, автобус, трамвай), плюс интеграция с Яндекс.Go для такси.
Причина: доступного готового источника данных, который бы одновременно покрывал транспорт Москвы с нужной детализацией (включая МЦК/МЦД) и не имел жёстких ограничений API, не нашлось — пришлось строить собственный пайплайн сборки GTFS-фида и разворачивать OSRM/OpenTripPlanner самостоятельно.

2. Функциональное требование № 8
Краткое описание изменения: планировалось редактирование и адаптация только собственных сохранённых маршрутов; стало — публикация маршрутов в открытый доступ, поиск и адаптация чужих опубликованных маршрутов другими пользователями, рейтинг маршрутов («звёзды»).
Причина: решено, что переиспользование и адаптация маршрутов другими пользователями (а не только автором) создают дополнительную ценность продукта и социальный слой, снижающий необходимость строить маршрут с нуля. Шеринг и система рейтинга превращает сервис в платформу.

3. Функциональное требование № 10 (новое)
Краткое описание изменения: планировалось — не предусматривалось вовсе, сохранение маршрута предполагалось только в рамках текущей сессии браузера; стало — полноценные аккаунты пользователей с регистрацией, подтверждением e-mail и восстановлением пароля.
Причина: постоянное хранение маршрутов и функция публикации/поиска чужих маршрутов (см. пункт 2) невозможны без привязки маршрута к учётной записи, а не только к сессии браузера — аккаунты оказались необходимой инфраструктурой, а не отдельной опциональной надстройкой.

4. Функциональное требование № 11 (новое)
Краткое описание изменения: планировалось — не предусматривалось; стало — отдельный мобильный режим «On It» для пошагового прохождения сохранённого маршрута с live-редактированием расписания по факту.
Причина: статичный план на день не учитывает реальные отклонения по ходу дня (очереди, задержки), и пользователю понадобился инструмент не только для планирования, но и для прохождения маршрута с гибкой подстройкой на месте.

5. Пользовательский сценарий № 1
Краткое описание изменения: планировалось — единая лента готовых маршрутов без уточнения структуры, вход в аккаунт не упоминался; стало — лента с вкладками «Все/Мои/Популярные/Рекомендованные», поиском по названию/автору/достопримечательности и отображением рейтинга; уточнено, что вход в аккаунт не обязателен для просмотра и создания, но нужен для сохранения и публикации.
Причина: прямое следствие пункта 2 (публикация/адаптация чужих маршрутов) — при большом числе опубликованных маршрутов просто «ленты» без структуры и поиска оказалось недостаточно.

6. Пользовательский сценарий № 10
Краткое описание изменения: планировалось — сохранение маршрута только в рамках текущей сессии браузера, без привязки к аккаунту; стало — сохранение в постоянном профиле пользователя с выбором публичности (публично/приватно) и возможностью получить рейтинг («звезды») от других пользователей.
Причина: см. пункт 3 — постоянное хранение и публикация невозможны без привязки маршрута к учётной записи, а не только к сессии браузера.

7. Пользовательский сценарий № 11 (новый)
Краткое описание изменения: планировалось — не предусматривалось исходными сценариями; стало — полноценный сценарий регистрации, подтверждения e-mail, входа и восстановления пароля.
Причина: см. пункт 3.

8. Пользовательский сценарий № 12 (новый)
Краткое описание изменения: планировалось — не предусматривалось исходными сценариями; стало — отдельный сценарий пошагового прохождения маршрута в режиме «On It» с живым сдвигом расписания.
Причина: см. пункт 4.
